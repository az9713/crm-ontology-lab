## Layer 1: Data

| term | plain definition (max 30 words) | what an FDSE would say (your CRM) | source URL(s) opened | conf. | note |
|---|---|---|---|---|---|
| Dataset | A wrapper around a set of files in a backing file system. It adds permissions, schema, version control, and updates over time. | "Your raw `crm_accounts` upload and your clean `accounts` output are both datasets; the Ontology reads the clean one." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | Can hold structured, semi-structured, or unstructured files. A media set is a different resource for media files. |
| Transaction | One atomic change to a dataset's files. It starts `OPEN`, then becomes `COMMITTED` or `ABORTED`. The docs compare it to a Git commit. | "Each run of your clean-accounts transform committed one transaction on `master`." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | Only one open transaction per branch at a time. |
| `SNAPSHOT` transaction | Replaces the full current view with a new set of files. It is the basis of batch pipelines. | "Your lightweight transforms write `SNAPSHOT` by default, so each build replaces all Opportunity rows." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | Each `SNAPSHOT` starts a new dataset view. |
| `APPEND` transaction | Adds new files to the current view. It cannot change existing files; a commit that overwrites a file fails. It is the basis of incremental pipelines. | "If you made the Activity log incremental, each sync would commit `APPEND` with only new rows." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | — |
| `UPDATE` transaction | Adds new files and can overwrite existing files. | "Don't let the sync overwrite files with `UPDATE`, or every downstream incremental transform falls back to a full rebuild." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | An `UPDATE` that overwrites files breaks incrementality downstream; an `UPDATE` that only adds files does not. |
| `DELETE` transaction | Removes file references from the current view. It does not delete the bytes in storage. Retention workflows use it. | "Deleting old Activity files with a `DELETE` transaction doesn't save storage; a retention policy does." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | — |
| Retention policy (added) | A policy that removes data in old transactions from storage. A `DELETE` transaction alone does not free storage. | "We'd set a retention policy on the raw uploads once the clean datasets are trusted." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | med | The datasets page marks *viewing* retention policies on a dataset as Beta. |
| Dataset view | The effective set of files on one branch at one point in time. A view starts at the latest `SNAPSHOT` and adds later transactions. | "The table you see in Dataset Preview is the latest dataset view of `opportunities`." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | Number of views = number of `SNAPSHOT` transactions. Do not confuse it with the "View" resource (next row). |
| View (resource) (added) | A separate resource that holds no files. When something reads it, it returns the union of its backing datasets. It can remove duplicates with a primary key. | "If the two Opportunity sources had the same schema, a View could union them, but we used a column-wise MDO." | https://www.palantir.com/docs/foundry/data-integration/views/ | high | A View can be a transform input, not an output. Same name as "dataset view", different thing. |
| Schema | Metadata on a dataset view. It tells readers how to parse the files and gives column names and field types. | "Your transform wrote a Parquet schema, so `closeDate` arrives as `DATE`, not `STRING`." | https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | Foundry does not check that the files match the schema. Field types: `BOOLEAN` … `TIMESTAMP`, plus `MAP`, `ARRAY`, `STRUCT`, `BINARY`, `DECIMAL`. |
| Data Connection | The application that syncs data from external systems into Foundry. It also sets up outbound writeback through webhooks and exports. | "You uploaded CSVs by hand; in production we'd pull Salesforce through Data Connection." | https://www.palantir.com/docs/foundry/data-connection/overview/ | high | Palantir's stated rule: ingest data as-is, then transform inside Foundry. |
| Source | One connection to an external system: its location (usually a URL), its credentials, and the worker that runs the compute. | "We'd create a CRM source with an API-token credential, then hang the syncs and webhooks off it." | https://www.palantir.com/docs/foundry/data-connection/core-concepts/ | high | — |
| Sync | A capability on a source that reads external data into Foundry. Types: batch (file or table), streaming, change data capture, media, Iceberg. | "A table batch sync would land Salesforce Opportunities as a raw dataset every hour." | https://www.palantir.com/docs/foundry/data-connection/core-concepts/ | high | The older "Tasks" concept is marked Sunset on the same page. |
| Agent | A program that you install in your own network and manage from Data Connection. It reaches systems that Foundry cannot reach directly. | "Your CRM is SaaS, so no agent; an on-prem ERP would need an agent proxy." | https://www.palantir.com/docs/foundry/data-connection/core-concepts/ ; https://www.palantir.com/docs/foundry/data-connection/set-up-agent/ | high | Agents now power agent proxy egress policies and the legacy agent worker. |
| Foundry worker vs agent worker (added) | The worker sets where source compute runs. Foundry worker runs in Foundry. Agent worker runs on a customer host and is Legacy. | "New sources go on Foundry worker; agent worker is legacy now." | https://www.palantir.com/docs/foundry/data-connection/core-concepts/ | high | **Renamed:** "direct connection" sources are now called "Foundry worker" sources. Agent worker sources cannot be used in code. |
| Egress policy (added) | A rule that says which external destinations Foundry worker sources may reach. Two kinds: direct connection and agent proxy. | "We'd add an egress policy for the CRM API host before the source can call it." | https://www.palantir.com/docs/foundry/data-connection/core-concepts/ | high | Agent proxy policies need a Foundry enrollment on Rubix (Palantir's Kubernetes infrastructure). |
| Export | Pushes data out of Foundry. File exports send dataset files, table exports send rows, streaming exports send stream records. | "To feed the cleaned Accounts back to the warehouse we'd set up a table export." | https://www.palantir.com/docs/foundry/data-connection/export-overview/ ; https://www.palantir.com/docs/foundry/data-connection/core-concepts/ | high | The core concepts page calls exports "the opposite of" the matching sync. |
| Pipeline Builder | Foundry's main point-and-click application for data integration. It builds pipelines from raw data to clean outputs. | "Your cleaning was in Code Repositories; most FDSE teams would start it in Pipeline Builder." | https://www.palantir.com/docs/foundry/pipeline-builder/overview/ | high | The docs say it uses Spark and Flink internally. It has its own data expectations and Ontology outputs. |
| Code Repositories | A web IDE over a Git repository. It does branches, commits, tags, and pull requests, with linting and checks. | "Your transforms and your TS v1 functions each live in their own Code Repository." | https://www.palantir.com/docs/foundry/code-repositories/overview/ | high | VS Code workspaces are an alternative editor. |
| Python transforms | Python code that turns input datasets into output datasets. It supports batch, incremental, libraries, and data expectations. | "Your `opportunities` transform is a Python transform with one input and one output." | https://www.palantir.com/docs/foundry/transforms-python/overview/ | high | — |
| Lightweight transform | A Python transform on single-node compute (pandas, Polars, DuckDB). The docs now treat it as the default. | "Your transforms are lightweight because the CRM tables are small; no Spark needed." | https://www.palantir.com/docs/foundry/transforms-python/lightweight-api-evolution/ ; https://www.palantir.com/docs/foundry/transforms-python/compute-engines/ | high | **Syntax changed:** `@lightweight` + `@transform` is the "legacy syntax" (still supported). The recommended form is `@transform.using(...)` (transforms ≥3.68.0, plugin ≥1.978.0). |
| Spark transform | A Python transform on distributed compute (PySpark). Use it when data is too big for one node. | "If Activities grew to billions of rows we'd move that one transform to Spark." | https://www.palantir.com/docs/foundry/transforms-python/lightweight-api-evolution/ ; https://www.palantir.com/docs/foundry/transforms-python/compute-engines/ | high | New syntax `@transform.spark.using` (transforms ≥3.95.0, plugin ≥1.1003.0). Some features exist only on lightweight (for example trained model outputs, incremental LLM API). |
| Incremental transform | A transform that reads only new input since the last build, by using build history. Input and output must be different datasets. | "Making Activity incremental needs the raw sync to stay `APPEND`-only." | https://www.palantir.com/docs/foundry/transforms-python/incremental-overview/ ; https://www.palantir.com/docs/foundry/building-pipelines/incremental-overview/ | high | The docs warn that incremental pipelines add development and maintenance cost. |
| Build | The mechanism that computes new versions of datasets. It orders the work, reads inputs, and writes outputs. | "Build `opportunities` on your branch first, then on `master`." | https://www.palantir.com/docs/foundry/data-integration/builds/ | high | — |
| Job / JobSpec | A job is one unit of work that computes one or more outputs. A JobSpec is the published definition of how to make the job. | "Committing your transform published a new JobSpec; the next build ran it as a job." | https://www.palantir.com/docs/foundry/data-integration/builds/ | high | Job states: `WAITING`, `RUN_PENDING`, `RUNNING`, `ABORT_PENDING`, `ABORTED`, `FAILED`, `COMPLETED`. Outputs of one job always update together. |
| Schedule | Runs builds again and again. A trigger sets when it runs. A run is Succeeded, Ignored, or Failed. | "Put a schedule on the clean datasets so the objects refresh after each upload." | https://www.palantir.com/docs/foundry/data-integration/schedules/ | high | "Succeeded" only means the build started. Pausing resets the trigger state. |
| Data Lineage | An interactive graph that shows how data flows between datasets, with schema, build time, and code. | "Open Data Lineage on `opportunities` and you'll see both raw inputs and the object type." | https://www.palantir.com/docs/foundry/data-lineage/overview/ | high | — |
| Health check | A check that validates data or pipeline health. Types: job-level, build-level, freshness. | "Add a freshness check on `accounts` so we know when uploads stop." | https://www.palantir.com/docs/foundry/data-integration/health-checks/ | high | — |
| Data Health / monitoring views (added) | The application that monitors resources and sends alerts. Monitoring views cover many resources by scope; health checks cover one resource in detail. | "A monitoring view on the CRM project would catch failed builds and failed actions together." | https://www.palantir.com/docs/foundry/observability/data-health/ | high | Monitors datasets, builds, functions, actions, automations, and more. |
| Data expectations | Requirements on a transform output, for example primary key or row count. If one fails, the build fails. | "Put a primary-key expectation on `opportunityId` so a duplicate fails the build, not the index." | https://www.palantir.com/docs/foundry/transforms-python/data-expectations-getting-started/ ; https://www.palantir.com/docs/foundry/pipeline-builder/dataexpectations-overview/ | high | In Python: `transforms-expectations` library, `Check`, `E.col(...)`. Single-node type checks use Polars types. |
| Dataset branch | A pointer to the latest transaction on one branch of a dataset. Most datasets have one root branch, `master`. | "Your transform branch wrote `opportunities` on its own dataset branch; `master` stayed unchanged." | https://www.palantir.com/docs/foundry/data-integration/branching/ ; https://www.palantir.com/docs/foundry/data-integration/datasets/ | high | **Not like Git:** the page says dataset branches cannot be merged. Code merges; data is rebuilt. Default name is `master`, not `main`. |
| Global Branching | One branch that spans many applications: pipelines, Ontology, functions, actions, Workshop. You test end to end, then merge to `main`. | "You built the Ontology changes on a global branch and merged them through a proposal into `main`." | https://www.palantir.com/docs/foundry/global-branching/overview/ ; https://www.palantir.com/docs/foundry/global-branching/core-concepts/ ; https://www.palantir.com/docs/foundry/global-branching/integrations/ | high | **Renamed:** previously "Foundry Branching". Creating or deleting non-Ontology resources on a branch affects `main`; Ontology entities do not. The OSDK is not branchable. |
| Proposal | A review request that merges a global branch into `main`. Checks and approvals must pass first. | "Your proposal passed the rebase check and the approvals, then you merged it." | https://www.palantir.com/docs/foundry/global-branching/core-concepts/ ; https://www.palantir.com/docs/foundry/ontologies/review-ontology-proposals/ | high | Creating one needs the branch `Owner` role or space `Administrator`. An ontology proposal is created automatically inside it. |
| Rebase (added) | Takes new changes from `main` into your branch and puts your branch changes on top. True conflicts need a manual choice. | "Someone edited the Account type on `main`, so you had to rebase before merging." | https://www.palantir.com/docs/foundry/global-branching/core-concepts/ | high | Non-conflicting changes resolve automatically. |
| Release management (added) | Moving versions of resources across separate environments (dev, test, prod). It complements Global Branching; it does not replace it. | "Branching gets the CRM into dev; release management moves it to prod." | https://www.palantir.com/docs/foundry/global-branching/overview/ | med | — |
| Foundry DevOps / product | DevOps packages Foundry resources as a versioned "product" with inputs and outputs. Release channels control which installations get a version. | "We'd package the CRM ontology, transforms, and actions as one DevOps product." | https://www.palantir.com/docs/foundry/foundry-devops/overview/ ; https://www.palantir.com/docs/foundry/devops/overview/ ; https://www.palantir.com/docs/foundry/devops/core-concepts/ | high | Products go into stores. Product types: Ontology, Use Case, Pipeline, Modeling. |
| Marketplace | The storefront where users find and install published products, with guided install and optional automatic upgrades. | "A client could install your CRM product from Marketplace and map their own raw datasets as inputs." | https://www.palantir.com/docs/foundry/marketplace/overview/ ; https://www.palantir.com/docs/foundry/devops/overview/ | high | A WebSearch result (thread not opened, so unverified) reports a Developer Tier object-type limit hit while installing a Marketplace tutorial bundle. See "What I could not confirm". |
| Virtual table (added) | A pointer to a table in an outside data platform. You query it without copying data into a Foundry dataset. | "If the CRM lived in Snowflake we might use a virtual table instead of a sync." | https://www.palantir.com/docs/foundry/data-integration/virtual-tables/ | high | Can also be a transform output. |
| Project and roles (added) | A Project is the main folder for work and the main boundary for role grants. Roles give users access to it. | "Keep raw, clean, and ontology resources in separate projects with different roles." | https://www.palantir.com/docs/foundry/security/projects-and-roles/ | high | Markings and organizations are mandatory controls on top of roles. |
| Development lifecycle phases (added) | The labels on every docs page: Beta, GA, Legacy, Sunset, Planned deprecation, Deprecated. Each label sets availability and support. | "That page is tagged Sunset, so existing customers only—don't build new on it." | https://www.palantir.com/docs/foundry/platform-overview/development-life-cycle/ | high | Sunset = no date set. Planned deprecation = date and migration path given. Beta = opt-in. |
| Upgrade Assistant (added) | Shows coming platform changes and the resources each change affects, with fix steps and owners. | "Check Upgrade Assistant for the OSv1-to-OSv2 intervention." | https://www.palantir.com/docs/foundry/upgrade-assistant/overview/ | high | The OSv1 page names a specific Upgrade Assistant intervention for migration. |
| Developer Tier limits (added) | Caps on the free tier, for example on action types, object types, and users. Control Panel → "Your Plan" shows the current values. | "You're on Developer Tier, so check Your Plan before you add more action types." | https://community.palantir.com/t/foundry-limits-me-to-max-60-action-types/6699/2 ; https://community.palantir.com/t/queries-regarding-free-tier-developer-account/5073/2 | low | No official docs page found. Forum reports 60 action types (2026-06-01). GA apps included; Beta apps need a support request (2025-09-19). 5-user and object-type caps come from search snippets only, unverified. |

## Layer 2: Ontology

| term | plain definition (max 30 words) | what an FDSE would say (your CRM) | source URL(s) opened | conf. | note |
|---|---|---|---|---|---|
| Ontology | An operational layer on top of datasets, virtual tables, and models. It connects them to real-world things such as customers, orders, and equipment. | "Your six object types, nine link types, and eight action types are your CRM ontology." | https://www.palantir.com/docs/foundry/ontology/overview/ ; https://www.palantir.com/docs/foundry/ontology/core-concepts/ | high | — |
| Digital twin | Palantir's own phrase for the Ontology: a model of the organization that maps data to real-world objects. | "The Ontology is the digital twin of the sales team—Accounts, Opportunities, and the actions reps take." | https://www.palantir.com/docs/foundry/ontology/overview/ ; https://www.palantir.com/docs/foundry/ontology/core-concepts/ | high | Palantir's metaphor, attributed. The overview page says "in many settings"; the core concepts page states it without that qualifier. |
| Semantic elements | The noun part of the Ontology: objects, properties, and links. | "The semantic layer is your six types and nine links." | https://www.palantir.com/docs/foundry/ontology/overview/ ; https://www.palantir.com/docs/foundry/ontology/why-ontology/ | high | why-ontology calls data the "nouns" and actions the "verbs". |
| Kinetic elements | The verb part of the Ontology: actions, functions, and dynamic security. | "Your eight actions and the TS v1 edit functions are the kinetic layer." | https://www.palantir.com/docs/foundry/ontology/overview/ ; https://www.palantir.com/docs/foundry/object-backend/overview/ | high | — |
| "Dynamic" (dynamic security) | In the docs, "dynamic" is an adjective: security policies computed at runtime for each request. It is not a third category beside semantic and kinetic. | "Row access for reps would be dynamic security, for example a restricted view on Opportunity." | https://www.palantir.com/docs/foundry/ontology/overview/ ; https://www.palantir.com/docs/foundry/ontology/why-ontology/ | med | I found no docs page that defines a "dynamic layer". why-ontology uses four parts instead: Data, Logic, Action, Security. See the falsify section. |
| Ontology Manager (OMA) | The application where you build and maintain the Ontology: object, link, action, and function types. URL path `/workspace/ontology`. | "Open the Opportunity type in OMA and check its datasources tab." | https://www.palantir.com/docs/foundry/ontology-manager/overview/ | high | Older name: Ontology Management Application (OMA). People still say "OMA". |
| Ontology Metadata Service (OMS) (added) | The backend service that holds the definitions of all ontology types (object, link, action, and more). | "OMS has the Opportunity definition; the object databases hold the rows." | https://www.palantir.com/docs/foundry/object-backend/overview/ | high | — |
| Object type | The schema definition of a real-world entity or event. It is like a dataset definition; one object is like one row. | "You have six object types: Account, Contact, Lead, Opportunity, SalesRep, Activity." | https://www.palantir.com/docs/foundry/object-link-types/object-types-overview/ | high | An object type can have no backing datasource if actions create all its objects. |
| Object type status (added) | A label for builders: `active`, `experimental`, or `deprecated`. New object types start as `experimental`. | "Your types are still `experimental`; flip them to `active` before anyone builds on them." | https://www.palantir.com/docs/foundry/object-link-types/object-type-metadata/ | high | — |
| API name (added) | The name that code uses for a type, property, or link side. | "Your TS v1 function calls `opportunity.account.get()` through the link's API name." | https://www.palantir.com/docs/foundry/object-link-types/object-type-metadata/ ; https://www.palantir.com/docs/foundry/object-link-types/link-types-overview/ | high | Each link side has its own API name. |
| Property | The schema definition of one characteristic of an object type. It is like a column; a property value is like one cell. | "`stage` and `amount` are properties on Opportunity." | https://www.palantir.com/docs/foundry/object-link-types/properties-overview/ | high | — |
| Base type | The data kind of a property. It sets which operations applications allow on it. | "`amount` has base type `Decimal`; `closeDate` has `Date`." | https://www.palantir.com/docs/foundry/object-link-types/base-types/ | high | All dataset field types except `Map` and `Binary`, plus Vector, Geopoint, Geoshape, Attachment, Time series, Geotemporal series, Media reference, Cipher text, Struct. Arrays allowed except Vector and Time series. |
| Primary key | The property that identifies each object. It must be unique and should be deterministic across builds. | "`opportunityId` is the primary key; we never generate it with row numbers." | https://www.palantir.com/docs/foundry/object-link-types/create-object-type/ ; https://www.palantir.com/docs/foundry/object-link-types/properties-overview/ | high | Edits attach to the primary key value. Changing the key prompts you to delete all edits. In OSv2, a duplicate key fails the Funnel batch pipeline. Date/timestamp keys are "Discouraged". |
| Title key | The property that is the display name of each object. | "Title key for Opportunity is `opportunityName`, so lists show names, not IDs." | https://www.palantir.com/docs/foundry/object-link-types/create-object-type/ | high | — |
| Render hints | Per-property flags that tell storage and applications how to treat the property: Searchable, Sortable, Selectable, Low cardinality, and others. | "Turn off Searchable on `notes` if nobody searches it; it makes reindex cheaper." | https://www.palantir.com/docs/foundry/object-link-types/metadata-render-hints/ | med | The page is written against OSv1 (Phonograph) and its reindex. I could not confirm how much of it applies under OSv2. |
| Backing datasource | The dataset (or restricted view, or stream) whose rows become objects of a type. | "`opportunities` is the backing datasource for Opportunity." | https://www.palantir.com/docs/foundry/object-link-types/object-types-overview/ ; https://www.palantir.com/docs/foundry/object-permissioning/multi-datasource-objects/ | high | Actions are not yet supported on object types backed by Foundry streams. |
| Multi-datasource object type (MDO) | An object type backed by more than one datasource. Foundry supports only column-wise MDOs: each datasource gives different properties for the same primary key. | "We backed Opportunity with two datasources: core fields from one, forecast fields from the other, joined on `opportunityId`." | https://www.palantir.com/docs/foundry/object-permissioning/multi-datasource-objects/ | high | OSv2 only. Datasets or restricted views only; no streams. Row-wise MDOs are not available; use restricted views for row-level access. |
| Link type | The schema definition of a relationship between two object types. One link type has two sides, so you traverse it both ways. | "Account ↔ Opportunity is one link type with an `opportunities` side and an `account` side." | https://www.palantir.com/docs/foundry/object-link-types/link-types-overview/ | high | No links across different ontologies. Do not make a second "reverse" link type. |
| Link cardinality | The intended count on each side: one-to-one, one-to-many, many-to-one, many-to-many. | "Eight of your links are many-to-one foreign keys; one is many-to-many." | https://www.palantir.com/docs/foundry/object-link-types/create-link-type/ | high | One-to-one is not enforced; it is only an indicator. |
| Foreign key link (added) | A link where a property on one type holds the primary key of the other type. Used for one-to-one and many-to-one. | "Opportunity has `accountId`, so Account ↔ Opportunity is a foreign key link." | https://www.palantir.com/docs/foundry/object-link-types/create-link-type/ | high | To change this link in an action, modify the foreign key property (see Layer 3 "Create link" row). |
| Join table dataset (many-to-many) | A dataset with one column per side's primary key. It backs a many-to-many link. | "Contact ↔ Opportunity is backed by the `opportunity-contacts` join dataset." | https://www.palantir.com/docs/foundry/object-link-types/create-link-type/ | high | Needed if users must edit the many-to-many link. | Object-backed link | A link stored as its own object type, so the link can carry extra properties. It builds on many-to-one links. | "If line items need `quantity` and `discount`, make an OpportunityLine object-backed link instead of a plain join table." | https://www.palantir.com/docs/foundry/object-link-types/create-link-type/ | high | Prerequisite: two many-to-one links from the backing object type to each side. | Interface | An Ontology type that describes a shape (properties, link and action constraints) that many object types implement. | Shared property type | One property definition used on many object types. | Value type | A reusable wrapper around a field type that adds meaning and constraints, for example an email regex. | "An `Email` value type would validate Contact emails in the pipeline and in actions." | https://www.palantir.com/docs/foundry/object-link-types/value-types-overview/ | high | Scoped to a space. **Not available for the Default ontology.** Can constrain action parameters. |

## What would falsify / what is missing

### Terms whose status changed (check these before you say them to an FDSE)

1. **Object Storage v1 (Phonograph).** Two pages say OSv1 "will be unavailable after June 30, 2026". On 2026-10-11 the pages still show the tag Planned deprecation, not Deprecated. Reading A: the date passed and the docs tag is not updated. Reading B: the date moved and the text is not updated. I cannot tell which. Say "OSv2" for anything new.
2. **Foundry Branching → Global Branching.** The overview gives the old name only once, in brackets. Standalone ontology branches (formerly called "ontology proposals") are being sunset. Today an ontology proposal is a child of a Global Branching proposal.
3. **Lightweight syntax.** `@lightweight` is now "Legacy syntax" (still supported). `@transform.using` is the new default for lightweight. Spark now has its own form, `@transform.spark.using`. The compute-engine page links PySpark docs in a separate `transforms-python-spark` section.
4. **TypeScript v1.** The docs recommend migrating to v2. TS v1 lacks interfaces, OSDK, staged writes, deployed mode, language-model proxy, and first-class platform-SDK auth. Your function-backed actions work today, but an FDSE will likely ask "why v1?".
5. **Submission criteria** were "validations". **Object Monitors** are Sunset in favor of Automate. **Foundry Rules** was "Taurus", and its time series rules are Sunset. **Agent worker** is Legacy. **"Direct connection"** is now "Foundry worker".
6. **Beta items you might call GA by mistake:** ontology-defined derived properties, direct datasources, staged writes, interface action type constraints, viewing dataset retention policies.

### Things a learner is likely to get wrong

- "Dataset view" (the files of one branch at one time) and "View" (a resource that unions datasets) are two different things.
- Dataset branches default to `master`; Global Branching merges into `main`. The docs say dataset branches **cannot be merged**, which breaks the "Git for data" analogy the same docs use.
- The Create link / Delete link rules work only on many-to-many links. A foreign key link changes through a Modify object rule on the key property.
- "Writeback" has two meanings: (a) the OSv1 writeback dataset, (b) a webhook that writes to an outside system before edits apply.
- Action log = the decision and its context. Edit history = every edit, from any source.
- OSDK (generated, typed, scoped to your ontology) and the Foundry platform SDK (`foundry-platform-sdk`, general API) are different tools.
- "Semantic / kinetic / dynamic": the docs name two element groups. Semantic = objects, properties, links. Kinetic = actions, functions, dynamic security. "Dynamic" is an adjective on security, not a third group. why-ontology uses a different four-part split: Data, Logic, Action, Security. If an FDSE says "the three layers", ask which split they mean.

### Terms with no public definition (possible internal slang)

- **FOO (functions on objects):** the docs say the term is used loosely and has no formal meaning.
- **"Dynamic layer" of the Ontology:** no docs page that I opened defines it.
- **"Phonograph", "Funnel", "OMS", "OSS":** public, but they are internal service names. FDSEs use them; end users see "Object Storage v1/v2" and "Ontology Manager".

### What I could not confirm

- **Developer Tier limits.** There is no official docs page. Palantir Community threads report: a cap of 60 action types ("one of the limits of DevTier", reply dated 2026-06-01, https://community.palantir.com/t/foundry-limits-me-to-max-60-action-types/6699/2); "check Control Panel → Your Plan" for current limits; GA apps included, Beta apps need a support request (reply dated 2025-09-19, https://community.palantir.com/t/queries-regarding-free-tier-developer-account/5073/2). The WebSearch summary also listed a 5-user cap and an object-type cap, but I did not open those threads, so treat them as unverified. Your 8 action types are below the reported 60. Confidence: **low**.
- **Value types on Developer Tier.** The docs say value types are not available for the Default ontology. I do not know if your Developer Tier ontology is the Default one.
- **Render hints under OSv2.** The page describes only OSv1 reindex behavior. I did not find an OSv2 statement.
- **Undo of an action (resolved).** The edits page says you cannot undo one edit directly. The action-reverts page adds a narrow exception: an Undo button in the success toast, OSv2 only, same user only, before any later edit to the object. Both statements are true; they describe different scopes.
- **`branch` parameter on Apply Action.** I saw it in the WebFetch summary of the API page, not in my own grep. Confidence: med.
- **RID.** I saw only an example RID format. I did not open a page that defines it.
