2. Design stories from the CRM build

A person with years on projects talks in trade-offs, not definitions. Each story states a design decision in the CRM build, a 30-second "Say it" version, the trade-off, and the follow-up question to expect.

2.1 Fix types in the pipeline, not in the ontology

Design
Each property has a base type, and its backing column must match it. When the two disagree, change the transform output, not the ontology. In the CRM build the money columns annualRevenue and amount are written as float64 and mapped to double properties.

"The backing column type has to match the property base type, so we cast in the transform and kept the ontology clean."

Trade-off A double cannot hold exact cents. For real money, keep a decimal type end to end.

Expect "Where do you fix a type problem: pipeline or ontology?" Answer: in the pipeline. The ontology reads what the pipeline writes.

2.2 One object type, two datasources

Design
Opportunity is backed by the CRM export (opportunities) and by the e-sign export (esign-contracts). Both share the primary key opportunityId. The e-sign columns supply contractSigned and contractSignedOn. An opportunity with no e-sign row has null in those properties. Multi-datasource object types need Object Storage v2.

"Opportunity is a multi-datasource object type: the CRM export backs most properties and the e-sign export backs the contract properties, joined on the primary key. Each source keeps its own lineage."

Trade-off The alternative is one joined dataset in the transform. That is simpler for the ontology, but it couples two source systems in one pipeline.

Expect "Why not join in the pipeline?"

2.3 Put the owner in the action as a parameter

Design
The rule is "only the record owner or a sales manager". Each owner-checked action takes an object parameter owner (SalesRep). The submission criteria check owner.salesRepId = the record's ownerId AND owner.foundryUserId = the current user. A member of the group sales-manager passes without the owner check.

"We pass the owning rep in as an object parameter and pin it to the record's ownerId. The caller cannot fake ownership, because the first condition binds the parameter to the record."

Trade-off One more parameter on the form. The alternative is a function that checks ownership in code, but then the rule is hidden from the action's submission criteria.

Expect "Why not just check it in a function?"

2.4 Write skew in assign-lead, and the guard write

Design
A rep can hold at most 3 open leads. assignLead counts the rep's assigned leads, then writes the lead. Two assignments at the same time can both read "2 of 3" and both succeed. This is write skew: each transaction reads a set but writes outside it. The design: the function also writes lastLeadAssignedAt on the SalesRep, so two concurrent assignments for one rep write the same object and one of them conflicts.

"The cap check reads a set of leads but writes only one lead, so under snapshot isolation two assigns could both pass. A guard write on the rep object makes concurrent assigns collide."

Trade-off The guard write serialises assignments per rep. That is acceptable for a sales team. The concurrency test is not built yet.

Expect "How do you know it works?" Honest answer: the design follows from the isolation rules; a concurrent test is still to do.

2.5 One writer for a derived number

Design
openLeadCount on SalesRep could be written by the pipeline, by actions, or by both. The transform is the only writer. assign-lead counts the leads at run time instead of trusting the stored number.

"Pipeline-derived properties have one writer. If actions also edited openLeadCount, the next build and the user edits would fight. So actions compute live and the pipeline owns the column."

Expect "What happens to a user edit when the backing dataset rebuilds?" (Look up edits and writeback in layer 2.)

2.6 Branch, test, propose, merge

Design
All ontology, transform and function changes go on one global branch. The actions are tested against branch data through the API with a branch parameter and VALIDATE_ONLY. The change ships to main through one proposal.

"We developed on a global branch, validated every action against branch data, and shipped through a proposal, so main only ever saw reviewed changes."

Expect "How do the functions follow the merge?" → story 2.7.

2.7 Point actions at a function version range

Design
The function-backed actions reference a version range of the function, not one fixed version. When the branch merges, the version published on main falls inside the range, so the actions need no manual repoint.

"Function-backed actions reference a version range, so when the proposal merged, the actions picked up the function published on main."

Trade-off A fixed version protects against an unexpected change; a range is easier across branches.

2.8 Raw layer, clean layer, key checks

Design
7 raw exports (201 rows) with planted mess are cleaned by one pandas function per dataset. Each clean output has a primary-key check. The cleaning treats an empty value and a null as the same thing. Locally, clean(raw) equals the clean CSVs for all 7 datasets, and 8 deliberate code mutants are all caught.

"We land raw exports untouched, clean in a transform, and put a primary-key check on every output, so a duplicate key fails the build instead of reaching the ontology."

Expect "What happens to the object type if two rows share a primary key?"

2.9 An object type that only actions create

Design
Activity has no source system. Its objects are created only by the action log-activity.

"Activity is created only through an action, so it lives in the ontology's edits; there is no source system for it."

Trade-off No pipeline history for Activity. For analytics, export the edits to a dataset.

2.10 Roles in groups, ownership in data

Design
Two groups carry the roles: sales-rep and sales-manager. The transform adds a foundryUserId column to sales-reps, which maps each business rep to a platform user. The submission criteria use the groups for role rules and the property for ownership rules.

"Criteria check group membership for role rules and a user-id property on the rep object for ownership rules. The mapping from business identity to platform identity is data, maintained in the pipeline."

Expect "Where would that mapping come from at a real customer?" (An identity provider sync, not a hand-written table.)

2.11 "Why are your functions on TypeScript v1?"

Design
assignLead and convertLead are TypeScript v1 functions. The current public docs recommend TypeScript v2. v1 has no interfaces, no OSDK, no staged writes, and no deployed mode.

"For anything new I'd use TypeScript v2, because v1 can't use interfaces or the OSDK, and an OwnedRecord interface is the next step for this model."

Expect This question, almost certainly. Show that you know the limits of your own choice.

11. Traps: renames, wrong ideas, unconfirmed items

Terms whose status changed (check these before you say them to an FDSE)

  1. Object Storage v1 (Phonograph). Two pages say OSv1 "will be unavailable after June 30, 2026". On 2026-10-11 the pages still show the tag Planned deprecation, not Deprecated. Reading A: the date passed and the docs tag is not updated. Reading B: the date moved and the text is not updated. I cannot tell which. Say "OSv2" for anything new.
  2. Foundry Branching → Global Branching. The overview gives the old name only once, in brackets. Standalone ontology branches (formerly called "ontology proposals") are being sunset. Today an ontology proposal is a child of a Global Branching proposal.
  3. Lightweight syntax. @lightweight is now "Legacy syntax" (still supported). @transform.using is the new default for lightweight. Spark now has its own form, @transform.spark.using. The compute-engine page links PySpark docs in a separate transforms-python-spark section.
  4. TypeScript v1. The docs recommend migrating to v2. TS v1 lacks interfaces, OSDK, staged writes, deployed mode, language-model proxy, and first-class platform-SDK auth. Your function-backed actions work today, but an FDSE will likely ask "why v1?".
  5. Submission criteria were "validations". Object Monitors are Sunset in favor of Automate. Foundry Rules was "Taurus", and its time series rules are Sunset. Agent worker is Legacy. "Direct connection" is now "Foundry worker".
  6. Beta items you might call GA by mistake: ontology-defined derived properties, direct datasources, staged writes, interface action type constraints, viewing dataset retention policies.

Things a learner is likely to get wrong

  • "Dataset view" (the files of one branch at one time) and "View" (a resource that unions datasets) are two different things.
  • Dataset branches default to master; Global Branching merges into main. The docs say dataset branches cannot be merged, which breaks the "Git for data" analogy the same docs use.
  • The Create link / Delete link rules work only on many-to-many links. A foreign key link changes through a Modify object rule on the key property.

Dataset built

A wrapper around a set of files in a backing file system. It adds permissions, schema, version control, and updates over time.

Your raw crm_accounts upload and your clean accounts output are both datasets; the Ontology reads the clean one.
Transaction

One atomic change to a dataset's files. It starts OPEN, then becomes COMMITTED or ABORTED. The docs compare it to a Git commit.

Each run of your clean-accounts transform committed one transaction on master.
SNAPSHOT transaction

Replaces the full current view with a new set of files. It is the basis of batch pipelines.

Your lightweight transforms write SNAPSHOT by default, so each build replaces all Opportunity rows.
APPEND transaction

Adds new files to the current view. It cannot change existing files; a commit that overwrites a file fails. It is the basis of incremental pipelines.

If you made the Activity log incremental, each sync would commit APPEND with only new rows.
UPDATE transaction

Adds new files and can overwrite existing files.

Don't let the sync overwrite files with UPDATE, or every downstream incremental transform falls back to a full rebuild.
DELETE transaction

Removes file references from the current view. It does not delete the bytes in storage. Retention workflows use it.

Deleting old Activity files with a DELETE transaction doesn't save storage; a retention policy does.
Retention policy

A policy that removes data in old transactions from storage. A DELETE transaction alone does not free storage.

We'd set a retention policy on the raw uploads once the clean datasets are trusted.

The effective set of files on one branch at one point in time. A view starts at the latest SNAPSHOT and adds later transactions.

A separate resource that holds no files. When something reads it, it returns the union of its backing datasets. It can remove duplicates with a primary key.
