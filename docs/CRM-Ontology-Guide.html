1. What the project is

The project teaches the Palantir Ontology. The method is to build a small CRM (customer relationship management) system "as close to Palantir's implementation as possible". A CRM records sales reps, the companies they sell to, the people at those companies, new leads, and deals.

An ontology, in Palantir's sense, is a layer on top of tables. A table row becomes an object (for example one Opportunity). A foreign key becomes a link (Opportunity → Account). A permitted change becomes an action (for example "Close opportunity as won"). An action has rules that say what it writes, and criteria that say who can run it and when. Users and applications change data only through actions. So the business rules live in one place, not in each application.

The project has two layers:

  1. A local schema in crm_ontology/. build_ontology.py writes ontology.json in Palantir's public OntologyFullMetadata shape: 6 object types, 9 link types, 8 action types, 1 interface. check_ontology.py validates it against Palantir's own SDK models (foundry-platform-sdk 1.108.0). Every key that is local design, not Palantir's public shape, starts with x-local.
  2. A real build on a free Foundry Developer Tier (AIP Now) enrollment. It holds 7 raw datasets, 7 clean datasets, 6 object types, 9 link types, 8 action types, 2 TypeScript functions and 2 user groups.

Status

The work was done on global branch crm-ontology-v1. Proposal "CRM ontology v1" was merged to main on 2026-10-11. The merge page showed 23 ontology entities Merged and crm-functions Merged.

2. The pipeline, end to end

In Foundry, data does not go straight into the ontology. A source system exports raw data. A transform cleans it. The object types read the clean output. Actions then write edits on top of the objects.

7 raw datasets201 rows. Two simulated source systems: a CRM (6 tables) and an e-signature system (1 table). All columns are strings.
→
repo crm-transforms7 Python lightweight transforms. Each output has a primary-key check that fails the build on a duplicate key.
→
7 clean datasets164 rows. Typed columns (date, timestamp, int, boolean, double).
→
6 object types + 9 linksEach object type reads a clean dataset. Activity has no dataset.
→
8 actions + 2 functionsThe only way to change objects. Criteria use 2 user groups.

Lineage. Five clean datasets each read one raw dataset. Two read a clean output too:

  • crm_users + clean leads → sales-reps. The transform counts each rep's open leads from the clean leads.
  • esign_envelopes + clean opportunities → esign-contracts. The transform drops envelopes for deals that the CRM does not know.

For each of the 7 datasets, the MD5 of the sorted rows in Foundry equals the MD5 of the local file crm_ontology/data/<name>.csv.

7. The two functions

Repo crm-functions, TypeScript v1. Code: crm-functions/functions-typescript/src/index.ts, class CrmFunctions.

FunctionWhat it does
assignLead(lead, rep)Refuses a lead that is not new. Counts the rep's leads with status assigned at run time. Refuses when the count ≥ maxOpenLeads. Sets the owner and status. Writes rep.lastLeadAssignedAt as a guard, so two concurrent assignments to one rep edit the same object and conflict.
convertLead(lead, opportunityName, amount, closeDate, owner?)Refuses a lead that is not assigned and an amount ≤ 0. Creates acct-<leadId>, ct-<leadId>, opp-<leadId> (stage prospecting, probability 0.1), links the contact to the deal, and sets the lead to converted.

Why openLeadCount is not edited (decision 2026-10-10, option 3). The transform is its only writer. If an action also wrote it, the next build and the action edit could disagree, and Foundry's default "Apply user edits" would keep the edit over a newer CRM value. So assignLead counts the leads itself.

8. Who can do what (identity rules)

Two user groups exist: sales-rep and sales-manager. The test user is in both. Only one Foundry user exists.

The problem. ownerId holds CRM ids such as rep-ana, not Foundry user ids. Criteria cannot follow links.

The fix.

  1. The transform adds foundryUserId to sales-reps (FOUNDRY_USERS in crm-transforms/transforms-python/src/myproject/datasets/crm.py). Only rep-ana maps to a user.
  2. Each owner-checked action gets an optional object parameter owner (SalesRep).
  3. The criterion is ANY( current user in sales-manager, ALL( owner.foundryUserId = current user id, owner.salesRepId = <record>.ownerId ) ).

The second condition binds owner to the record. So a caller cannot pass another rep to pass the check.

Ontology, database, graph database: the differences

Short answer. The data shape is the same as a property graph. This CRM fits into a graph database such as Neo4j, or into 7 relational tables, with no loss of data. The differences are in what surrounds the data: where the data is stored, which system is the source of truth, how a write happens, who can write, and how a reader follows the data back to its source.

Which one to use

  • Graph database: the main questions are about paths. Example: "which contacts are 3 hops from rep-ana". That is one Cypher query. In the ontology it is 3 Search Around steps.
  • Relational database: one application owns the data and needs multi-statement transactions.
  • Ontology: several source systems feed one model (here: the CRM and the e-signature system), and many users and applications change it through checked actions.

Trade-offs: choose one, give up the other two

Each block below assumes that you use only one of the three. It lists what you get, and what you lose compared with each of the other two. The examples use this CRM.

Ontology only (no graph database, no SQL database)

  • You get: one model over several source systems (the CRM export and the e-signature export join into one Opportunity). Writes go only through checked actions, so the rule "close only with a signed contract" holds for every app. User edits stay when the build replaces the datasets. Lineage leads from each value back to its raw export.
  • You lose compared with a graph database: pattern queries and paths of variable length. "Contacts 3 hops from rep-ana" becomes 3 Search Around steps in code. There are no shortest-path or centrality algorithms. A link cannot hold data; a relationship with data needs its own object type.
  • You lose compared with a SQL database: ad hoc SQL over the live objects, and the large set of SQL tools. Freshness: the objects are only as new as the last build of the backing datasets. Portability and cost: the model lives in a commercial platform (here the free Developer Tier, with its limits); the portable copy of the model in this project is ontology.json.
  • Choose it when: several systems feed the data, many users and apps change it, and the rules must hold for all of them.

Graph database only (no ontology, no SQL database)

  • You get: fast multi-hop queries, path algorithms, and properties on relationships (for example, the role of a contact on a deal on the link itself). The schema can change without a migration.
  • You lose compared with an ontology: a governed write path. The rule "close only with a signed contract" must live in each application, and a client with write access can skip it. A reload from the source systems overwrites user changes unless you write merge logic. You must build lineage and per-action permissions yourself.
  • You lose compared with a SQL database: the standard language for totals and reports ("pipeline amount by stage"); most reporting tools speak SQL, not Cypher. Weaker schema checks by default: a typo such as negotation in stage enters unless you add a constraint. Fewer people can read the queries.
  • Choose it when: the main questions are about connections: who knows whom, account hierarchies, referral chains.

SQL database only (no ontology, no graph database)

  • You get: a mature, low-cost, standard store. Multi-statement ACID transactions. Strong constraints: CHECK (stage IN (...)), foreign keys, NOT NULL. Every reporting tool connects to it, and totals by stage or by rep are one query.
  • You lose compared with an ontology: you write the business layer yourself: the action checks, the owner-or-manager permission, the merge of user edits with new source data, and the lineage. The rules spread across application code, and each app can apply them differently.
  • You lose compared with a graph database: deep traversal. Each hop is one more join; any depth needs a recursive CTE, which is longer to write and slower as the depth grows.
  • Choose it when: one application owns the CRM data, and reports and transactions matter more than relationship queries.

The three are often combined: a SQL database as the source system, an ontology over the exported data for governed use, and a graph database for path analysis. This project uses two of the three roles: the raw CSV exports stand in for the source systems, and Foundry holds the ontology. It has no graph database.

An ontology is not a type of database. It is a model with rules over data that other systems store. A graph database stores the graph itself. Sources: the public ontology notes in research/palantir-public-model.md and the build of this project.
